DATAMAN

DATAMAN is a general purpose data base and record manager.  It consists of a database server that runs on a Linxu/Unix system and a library of routines that are bound into an application program to be called at run time.  The package provides for both indexed and sequential record access.  The individual files that DATAMAN handle have a physical limit of approximately four billion bytes. The routines also provide for multi user capabilities in record locking. Internal file and record locking are performed invisibly to the user during file and index updating.  The user may also protect a record from other users trying to protect the same record at the same time.  This and the proper use of the "work file" (described later) makes this package ideal for transaction processing as well. 

This manual is for those who have no experience with either the EDITOR, or ET programming languages, or the DATAMAN database package.  For those that have used the EDITOR, EASY C, or the ET languages, this library emulates the verbs of those languages.  The first section describes the file structure expected by the manager and client routines, the files used, and their structure.  Section two discusses basic I/O.  The third section discusses the basic usage of the package, and section four each user routine.  The last section covers miscellaneous topics.



1 FILES

This section covers many aspects about files. The first topic is the root file structure followed by a discussion of the different directories usually found in the root, and the differences between a work and master file.

        1.1  ROOT FILE STRUCTURE
          The DATAMAN database client routines expect there to be an environment variable named ROOT.  This value should contain the "root" directory path to your database on the server.  Under this root there must exist a directory named files, and one named index.  These contain the database files and indices, respectively.  There also is sometimes another directory named init.  This directory contains the initialization files for your database.

          EXAMPLE
          To set up the "root" of the database structure, at your prompt issue the command:

            ROOT=/var/databases/accounting

          This tells DATAMAN that the (accounting) database it will be operating on will be found under the /var/databases/accounting directory on the host system.  Alternatively, you may use the -r switch when starting your program to tell the database manager where the database resides.

     1.2  FILES DIRECTORY
          This directory will contain the data files used in your database.  Data files contain information in fixed length record formats.  There may be from one to sixty-three record formats defined for each file.  By use of these record formats the user may simulate variable length records, group various types of data together, and designate a particular file structure.  The meaning of designating a particular file structure is that the user may insert records into the database where he wants.  If there are two or more different record formats with related information, the user may group those records together, thus eliminating the need for a key on each separate record.  There is a functional limit of between 5000 and 7000 total fields that the user may actually define in a file.  Each file must have at least one record in it.  Thus, to generate a data file there is a utility named mkdf that will create a data file from an initialization file.  

          EXAMPLE
          Assume there will be a file containing the English translations of the Latin instructions used for prescriptions.  This file would contain one record format.  This would perhaps have the English translation, the Latin SIG, and possibly a code number.  Fields 1, 2 and 3 would each be 20 characters long, to contain all of  the possible information, field 4 would be 7 characters long and contain the Latin SIG and field 5 would be 3 bytes long and contain a numeric code.  Now if, for example, you lived in an area that was heavily populated with Spanish speaking people, you might want the same information in Spanish as well.  Because you may designate your own file structure, you place the second record immediately after the first to save space.  Because you know where the second record format is you don't need the Latin SIG in the format or the numeric code either, or even a key on the second record.  All that is needed is the Spanish translation.

     1.3  INDEX DIRECTORY
          This directory contains the indices to the database.  All data is initially retrieved from master data files by referring to a key in an index.  The index may refer to data contained in up to 99 different files.  Internally all keys in an index are the same length.  Any keys that are shorter than the maximum length defined are padded with null characters.  Therefore it may be advisable to have several indices, and to group keys with approximately the same length into the same index. DATAMAN will therefore allow an application to open and reference up to six different indices at once.  As a result a database may refer to up to 594 data files at any one time.

     1.4  INIT DIRECTORY
          This directory usually contains the initialization files used to create data files.  Since all data files must contain at least one record, all files must have an initialization file.  Usually, these files contain control information and counters for dynamic files, and all of the data for static files.  Each field in these initialization files are separated by colons (:), and each line must be terminated with a new line ('\n') character.  The first field on each line is the number of the record format that will be generated for this information.  After the record format number is the first colon.  Then follows the data for the first field.  All fields must either be filled to the maximum length or have zero length.  A zero length field infers that there is no information, and will be blank filled.  Otherwise the field will be generated with the information found between the first colon and the next.  The process repeats itself for each field in the record format, or until a line terminator is found.  If there are any unfilled fields when the line terminator is found, those fields are blank filled.

          EXAMPLE
          The initialization for the latin translation file might look as follows:
               1::::~~~~~~~:000:
          The '1' represents the record format number.  The four colons together represent three empty fields.  The tilde (~) character was selected as the SIG because it is the greatest printable character, and the '000' for field 5 is a counter signifying that there are no codes used yet.  There is no initialization for record format 2 because no initial information needed for this record.

     1.5  MASTER vs WORK FILES
          There are two types of files used in the DATAMAN database.  The first is referred to as the MASTER file.  This is a file that is currently being pointed to by an open index.  Records may be retrieved from these files only by referencing the index name.  These files are opened and closed as needed as the index refers to them, and a process may refer to all MASTER files during a session.  A WORK file is opened at the beginning of the process, and the first record of that file is read into memory.  This file is never referenced by an index, and is always the only work file.  The only exception to this is for sort routines.  These routines create indices, and require all files that are to be included named as work files.  The procedures release and sort will only operate on work files.  The records in MASTER files are referred to through the mfld array and the records of the WORK files are referred to through the wfld array.
2.   INPUT AND OUTPUT
     This section describes the basic input and output devices used by DATAMAN.  First described will be the terminal i/o followed by data file i/o.

     2.1  TERMINAL I/O

          2.1.1     OUTPUT
               Most terminal output is accomplished through a function named show.  This function takes a variable number of arguments.  The arguments come in groups of three.  The first of the group is the row to begin the display, the second is the column to begin the display, and the last is the string to display.  They MUST follow in this order.  There are also two predefined strings that show uses.  The first is TOP.  This string informs show to clear the screen from the current cursor position.  The next is EOL.  This clears from the current cursor position to the end of the current line.  The last argument of show must be the manifest constant ENDLIST.  This informs show that the argument list is now exhausted.  Another type of screen output is the pause.  This positions the cursor and writes to the screen, sounds a bell, and waits for the user defined 'help' key to be entered.

          2.1.2     INPUT
               Terminal input is performed by a function named accept.  The proper syntax for accept is:
               accept(row,col,str,mode) else ...
               where row and col is the screen position to begin the read.  The str argument is the destination buffer, and mode is any of the manifest constants ANY, UPPER, LOWER, or NUMERIC.  Any of these may also be or'd with the constant NOECHO to prevent input being echoed to the screen.  When accept is called the current length of the string pointed to by str is the maximum length that will be read.  An "input template" is displayed when accept is called.  This displays the longest input possible.  The only time the else clause is performed is when the input is terminated abnormally by entering the 'help' key.  This key is user defined and is used for backing out of accepts and pauses.  Input is terminated after either the 'help' key is entered (causing an abnormal return), a normal line terminator is entered (i.e. a new line), a function key is entered (in the proper case), or the maximum number of characters is entered.

          2.1.3     HELP
               This key may be misnamed but is applicable.  Help is defined by an environment variable named HELP.  There are several different ways to define your help key.  The simplest is as a control character.  If the first character of the HELP variable is a '^' the next character is taken to be the 'help' control character.  For example, if HELP is defined to be "^W", then holding down the control key while depressing the 'W' key will generate the 'help sequence'.  The next is with a numeric sequence.  This is usually for defining a function key as 'help'.  If the environment variable is not set the default is the 'home' key.

     2.2  DATA FILE I/O
          Input and output from data files is completely automated.  The user, just by moving to a new record in the data base writes the old record, and retrieves the new.  All data is returned in character strings.  Data is returned as pointers to these strings in mfld[i] or wfld[i] for the master record, and the work record respectively.  The value i ranges from 1 to n where n is the highest field number defined.  Field number 0 is reserved.  For both types of files there are macros defined to set a 'dirty' bit for a record.  If this bit is set, then when moving to a new record, the data is rewritten.  This is to speed execution when reading several records that are not changed.  There is no error checking for data written beyond the end of a data field, consistent with the "C" language.  The user, in all cases is responsible for the integrity of the data fields. 
3.   USING DATAMAN
     This section discusses the basic flow of designing and implementing a database application using the DATAMAN package.  First is file layout, then follows generating a database, and then using the package in an application.

     3.1  DESIGNING A FILE LAYOUT
          The first thing to do when implementing a database application is to determine the data elements that will be used.  In an extremely simple charge account system the necessary data will include the account name, address, city, state, zip, and the account number.  There would also be transaction records.  These would include the transaction date, amount, location, and perhaps some sort of code.  The thinking is already in terms of different record formats.  The first would be a demographic record and the second the charge record.  The most logical way to organize this data base would be to have the demographic record immediately followed by multiple occurrences of the charge record.  This saves the need for keys on every record, and groups related data together.  All these considerations should be taken into account when designing your data base.

     3.2  GENERATING A DATABASE
          After all of the data elements needed have been defined, group related data into different files.  In the charge account system described above, there would be only one file.  In a large system, such as a pharmacy management system, there would be several files, for doctors, patients, the drugs and so forth.  Determine the structure of each file and the initial record needed for each file.  Next generate an input file as described  above, and execute the utility mkdf to generate the data file.  The usage of mkdf is:
               mkdf data_file input_file.i
          The ".i" extension is required.  All errors generated in this process are self explanatory.  If data_file existed previously, the file is regenerated, and the old data is lost.
          The next step in generating a data base is to determine the key elements in a file.  In the charge account system, the only key element would be the account number.    Possibly the account name would be of use as well, but is not necessary.  Then write a sort program that generates the index on the key fields using the appropriate DATAMAN procedures.

     3.3  USING DATAMAN IN AN APPLICATION
          The first application needed is in the database generation phase, and is the sort procedure.  This procedure generates the index used in the "file edit" procedures.  To begin a sort procedure the user must include the DATAMAN include file "sort.h".  The first sub procedure called in the sort routine is mkidx.  This creates an empty index with all the basic index information.  The procedure mkidx also defines the usage for sort procedures as being:
               sort_prog [-r root_dir] [-h host] [-length] idx_name file_1 [file_2 ...]
          where root_dir is the root directory of the database, host is the host where the database resides, length is the maximum key length allowed in the index, idx_name is the name of the index being generated, followed by the names of the files to be included in the index.  The -r root_dir will override the environment variable ROOT.  The -h host switch will override the DSERVHOST environment variable.  If neither are specified the database server is assumed to be 'localhost'.  The default value for length is 20, the minimum is one, and the maximum is thirty two.  The index may include 99 different files.  The two other most important functions used in the sort program are sort, and release.  The function sort places keys in the index, and release moves off the current work record and to the next.  If the current work record is the last in the file release tries to move to the first record in the next named file.  If the current record is the last in the last named file, the else clause of release is taken.  This signals an end condition to the sort program.  There is a function named when_file that is true when a new file is initially opened, and the current file name is contained in FILE.  File Edit programs are named as they are because they add, remove, or peruse data from the database.  All procedures in file edit routines must include the header file "dataman.h".  This defines the externals, and the macros for all of the functions.  The first procedure called here is init_dataman.  This processes the command line arguments and will initialize the DATAMAN process.  There are three major classes of functions used for retrieving data.  The first are the key retrieval functions, the next are the file retrieval functions, and the last are add and delete functions.

          3.3.1     KEY RETRIEVAL
               These functions all have roughly the same syntax; get(...) else ....  All these functions require an index name.  These functions will retrieve the named key (or the next, or prior) write the old record, and read the new record pointed to by the key if successful.  If the get is not successful the old record remains in memory, and the else clause is taken.  A key that is named in the get function must be built with the mk_key function.  A variable type key is typedef'd to use to insert the retrieved key into.  System keys may be saved in variables of type key as well.

          3.3.2     FILE RETRIEVAL
               These functions let the user walk through the database itself without changing the index key pointer.  When a user has defined a good file structure this can be much faster than doing a key search for every record.  The syntax is: forward (back) (idx_name) else ....  This will retrieve the next (or prior) record in the database and write
out the old record.  These functions may or may not take an index name.  If an index is named, the current record pointed to by that index is taken as a reference, and the next (or prior) record in the database is retrieved, and the old record written to the file.  If the current record is the last (first) in a database file, the current record is retained, and the else clause is taken.  If the manifest constant WFILE is used instead of an index name the forward or back is performed on the work file.

          3.3.3     ADD AND DELETE
               The add functions add either a record or a key to your database.  The function insert inserts a record into the database.  It takes the current record pointed to by an index as reference, writes the old record to the file, inserts a record before or after that record, and reads it into memory.  The other add function is include.  This inserts a key pointing to the current record of an index into an index which may not necessarily be the same index.  Basically you've gotten a record using index 1, and inserted a new record.  Because of your key size difference a key to the new record goes into index 2.  The user names index 1 as the source of the record and index 2 as the destination of the key.

               The delete function deletes a data base record from a data base file.  This also has the effect of removing all of the keys that point to that record.  To delete a key from the index, the function remove is provided.  This will only remove a key, it will not delete the associated data base record.  A key that points to a data base record that has been deleted will be removed at run time by trying to access that key.  So, to speed up processing, it is a good idea (though not necessary) to explicitly remove all of the keys pointing to a record that is to be deleted.

          3.3.4     TRANSACTION PROCESSING
               Transaction processing is facilitated in this package with the use of the work file.  This is a file where the current record is existent in all subroutines and procedures during the life of the program.  This makes it an ideal place to save data and information until the current transaction is complete.  At the end of the transaction, with the proper usage of the protect and clear functions, all other master files may be updated at one time without other users disturbing the data in the meantime.

                                                           ACCEPT

     Summary

          #include "dataman.h"
                or
          #include "sort.h"

          accept(row,col,acc,mode) else ...

          short int row,col,mode;
          char *acc;

     Description
          The accept function does screen positioned, keystroke polled input.

          Row and col is the row and column number to begin reading.  Acc is a character pointer (string) to the input buffer.  The length of the string currently pointed to by acc determines the maximum number of characters that accept will read.  Mode is a manifest constant describing the type of input.  The constant ANY will accept any printable character, while the constant LOWER will map all input to lower case.  UPPER will map all input to upper case, and NUMERIC will allow only numeric input.  Finally, the constant NOECHO may be or'd with any of these to suppress the echoing of input to the screen.  If the system defined 'help' key is hit the input buffer is set to zero length, the read is terminated, and the else clause is taken.  If a normal line terminator is
hit, acc is truncated to the number of input characters, and the else clause is skipped.  Function keys are returned in the first byte as the scan code or'd with 0200.

     Example
          
          #include "dataman.h"

          main(argc,argv)
          int argc;
          char **argv;
          {
              short int row,col;        /* row and column */
              char inpt[5];             /* input variable */
               ...
              row = 5;
              col = 15;
              memset(inpt,' ',4);            /* read 4 chars */
              *(inpt+4) = '\0';              /* end string */
              accept(row,col,inpt,UPPER) else {
                    flush()
                    return;
              }
               ...
          }


BACK                                                             

     Summary

          #include "dataman.h"

          back(idx_name) else ...

          char *idx_name;

     Description
          This procedure flushes the current record to disk and retrieves the data record preceding it to memory.  The string idx_name is the name of the index that points to the file that the user wants to back up, or the manifest constant WFILE.  The function back is not to be confused with the get_prior function.  The index refers to its MFRP, then checks if there is a record preceding this in the data base file.  If not, the current record is not flushed, and the else clause is executed.  If there is a revious record, the current one is flushed, the MFRP is decremented, and the new current record is read into memory.  If the index has no current record (i.e. a GET has not occurred) the diagnostic 'Initial GET not attempted' will display and the routine will terminate.  If idx_name is the manifest constant WFILE the operation will affect the work file.

     Example
          
          #include "dataman.h"

          main(argc,argv)
          int argc;
          char **argv;
          {
              key k_buff;
               ....
              get(idx1,k_buff) else {
                  pause(10,10,"Can't find key");
                  exit(0);
              }
              while (MFMT == 3) {
                  back(idx1) else       /* keep backing */
                     break;             /* first of file */
                  ...                   /* process record */
              }
          }


                                                            CLEAR

     Summary

          #include "dataman.h"

          clear(idx_name);

          char *idx_name;

     Description
          This function is used in a multi user environment.  The clear function removes the protection from a data record, allowing the user to "check in" a record that has been protected.  This is an unconditional clear; it will clear any protected record, regardless of who initiated the protect.  If for any reason the file is closed before the record is cleared, the record remains protected.  To provide for a users source code compatibility in the single user version, this function is implemented as a no-op.

     Example

          #include "dataman.h"

          main(argc,argv)
          int argc;
          char **argv;
          {

              key k_buff;
               ...
              get(idx1,k_buff) else {
                  pause(10,10,"Can't find key");
                  exit(0);
              }
              while(1) {
                  protect(idx1) else {       /* protect rec */
                      waste_time();          /* pend */
                      continue;              /* try again */
                  }
                  break;                     /* got protection */
              }
               ...                           /* process record */
              clear(idx1);                   /* clear protect */
          }


DELETE                                                           

     Summary

          #include "dataman.h"

          delete(idx_name);

          char *idx_name;

     Description
          This function deletes a database record from its database file.  If the index's MFRP points to nothing, the diagnostic "Initial GET not attempted" is displayed, and the procedure exits.  Otherwise the last accessed record is flushed to disk, and the current record that the index's MFRP points to is deleted from the database file.  If the MFRP points to the last record in a data base file, the pointer is decremented to the previous record, otherwise the MFRP points to the record that followed the deleted record. If the user attempts to delete the only record in the database file, a diagnostic will result, and the program terminates.  A call to delete will NOT remove all of the keys that point to the record.  If a key is referenced that points to a deleted record, the key will be removed at that time.  Otherwise only an explicit call to remove will do away with keys.

     Example
          
          #include "dataman.h"

          main(argc,argv)
          int argc;
          char **argv;
          {

              key k_buff;
              char inpt[7]
               ...
              remove(idx1,k_buff) else {
                  pause(10,10,"Can't find key");
                  exit(0);
              }
              delete(idx1);             /* delete the record */
          }


                                                            FATAL

     Summary

          #include "dataman.h"
          #include "sort.h"

          fatal(format,string);

          char *format, *string;

     Description
          The fatal function prints a fatal error message and terminates the current process. The format string follows the conventions of the 'C' printf function, but it accepts only one string as the "argument".  A related function, err, which generates messages from error codes, is also reserved to dataman.  

     Example

          #include "dataman.h"

          main(argc,argv)
          integer argc;
          char **argv;
          {

              char buff[10];                 /* key to build */
              key k_buff;                    /* key for get() */
               ...
              mk_key(k_buff, buff, strlen(buff));
              get("name_ix", k_buff) else
                  fatal("Can't get key %s\n",buff);
               ...
          }


FLUSH                                                            

     Summary

          #include "dataman.h"

          flush();

     Description
          The flush function flushes the contents of both the current work and master records to their respective files.  The records remain in memory after the call.  The main purpose is to force an update of the disk file before it would normally happen.  The most common use of this is at the end of a function, or program.  If flush is not called the last accessed record may never be updated in it's file.
     
     Example

          #include "dataman.h"

          main(argc,argv)
          int argc;
          char **argv;
          {

              short int row,col;        /* row and col to read */
              char input[5];            /* read buffer */
               ...
              accept(row,col,input,UPPER) else {
                  flush();              /* flush the record */
                  return;               /* return to main menu */
               }
          }


                                                          FORWARD

     Summary

          #include "dataman.h"

          forward(idx_name) else ...

          char *idx_name;

     Description
          The forward function retrieves the next record from a database file.  The function checks the named index's MFRP.  If it points to nothing, the diagnostic "Initial GET not attempted" is displayed, and the process terminates.  If a record follows the one pointed to by the index, the last accessed record is flushed to disk, the index's MFRP is incremented, and the new current record is read into memory.  This should not be confused with the get_next function.  If the MFRP points to the last record in a  particular file the current record is NOT flushed, and the else clause is taken.  If idx_name is the manifest constant WFILE this signifies that the file to be operated on is the 'work file', instead of an index file.

     Example

          #include "dataman.h"

          main(argc,argv)
          int argc;
          char **argv;
          {

              key k_buff;
               ...
              get(idx1,k_buff) else {    /* get a format 2 */
                  pause(10,10,"Can't get key");
                  exit(0);
              }
              do {
                  ...                   /* process rf 2 */
                   forward(idx1) else   /* get to next record */
                       break;           /* at EOF */
              } while (MFMT == 2);      /* do format 2 recs */
          }


GET                                                              

     Summary

          #include "dataman.h"

          get(idx_name,k_buff) else ...

          char *idx_name;
          key k_buff;

     Description
          This procedure retrieves a record associated with a key in an index file.  The data type 'key' has been defined through a typedef statement in the include file.  All keys used in get must be generated with the mk_key function.  If the named key is not a member of the index the current record remains in memory, and the else clause is taken.  If the key does exist, the index's KP is set to the new key, the MFRP is set to the record that the key refers to, and the record is read into memory.  Generic, and approximate key searches are fully supported.  To search for generic keys, an asterisk ('*') may be substituted for each individual character that is unknown.  An approximate key is just the first one or more characters.  The get function will retrieve the first key that matches the input up to the length of the input.

     Example

          #include "dataman.h"

          main(argc,argv)
          int argc;
          char **argv;
          {
              key k_buff;
               ...
              mk_key(k_buff,"1100**6",7);      /* generate key */
              get(num_ix,k_buff) else {      /* get a key */
                    ...                      /* not there */
               }
               ...

                                           MISCELLANEOUS #DEFINES

          There has already been mentioned several system defined 'variables', and constants,  The dataman header defines several useful 'functions' and variables.  The first two are KEY, and KEY_LEN.  The first is a structure of the internal key that dataman is currently using, and KEY_LEN is the internal length of that key.  When generating keys with the mk_key function, always use KEY_LEN as the length.  A related #define is FILE.  This is a pointer to the name of the file currently pointed to.

          MFMT and WFMT are both defined to display and test the format numbers of the master and work files.  MFMT displays the master file format, while WFMT displays the work file format.  DO NOT CHANGE THESE VALUES.  Serious database errors could result if the user alters the values in these variables.

          Next are the WHEN functions.  These are when_mfmt(x), when_wfmt(x), and when_file.  The when_fmt functions test if the current work or master format number equals the value x. The when_file is used in sort routines.  This is a true value when a new file is opened, and set to false when the first release is performed.

          There are two strings defined named TOP and EOL.  These may be passed as the string arguments to show to do screen clearing.  TOP will clear the entire screen from the point that the cursor is positioned in the row and column.  EOL will clear from the cursor position to the end of the line.

          Last are the field copy #defines.  They are named mstrcpy, mstrncpy, wstrcpy, and wstrncpy.  These copy one tring into another like the strcpy routines of similar name, but these also set a "dirty" flag for the master record (mstrcpy, and mstrncpy), or the work record (wstrcpy, and wstrncpy).  The dirty flag informs the manager that the record has been updated since last retrieved or flushed and that when moving to a new
record, or flushing the current record, to write the record to the database.  If the user would rather, he/she may use dirty_m, or dirty_w to manually set these flags.  If the flag isn't set the record will not be written to the database.

5    UTILITIES

     The utilities represent a good deal of support to the programmer.  They will help generate a database, analyze the current data base contents, clean up lost space, and edit the structure of the data base files.

     5.1  CLEAN
          This is a utility to update and clean the empty space out of data files and indices.  The usage is: 
               clean [-space] [Cleanfile]
          If Cleanfile is not included in the command line, the program searches the current directory for a file named Cleanfile.  Otherwise, the cleanfile is the one named in the command line.  Cleanfile describes the systems, and method to clean your database.  All spaces and tabs in the cleanfile are significant.  The -space argument is the amount of unused space in data files when re-organizing begins.  The default is five percent.  This
value may range from five to twenty five percent.

          The cleanfile consists of three sections headed by key words.  The key words are ROOT:, FILES:, INDICES:.  These key words must have no spaces before them and must have the trailing colon (:).  ALL of the lines after each heading key word line must begin with a tab (\t) character,and there must be one blank line between each section.  After the ROOT key word line, the next line defines the DATAMAN root directory.  This is the full path name to the parent directory of the files and index directory.  Next is an empty line followed by a line  with the FILES: key word.  The line(s) after this key
word name each file that will be checked and possibly rebuilt.  Each of these lines again must begin with the tab character.  Finally, comes the INDICES: section.  Each line here is the command line that will rebuild indices.  As a result, each sort procedure must be part of the application.  Following is a sample of a simple Cleanfile.


ROOT:
     /var/database/accounting

FILES:
     acct contacts sales

INDICES:
     acct_srt1 -20 name_ix acct
     acct_srt2 -10 num_ix acct

     5.2  DFEDIT
          This utility is used to examine and update a data file contents, or its structure.  The first use of this program should be to merely edit data.  It's use to change record links is highly discouraged.  Extreme caution should be used when editing the data file pointers.  Each data record points to the record preceding it, and following it.  A record with a back pointer of zero is the first in the file, one with the next pointer of zero is the last in the file.  It's menu of operations is fairly simple.  When the program is first initiated the title names the file being edited, and the user is positioned before the first record of the
data file.  At the prompt the user may enter either a record link number or one of the function keys.  Function key 1 moves to the record prior to the current one, key 2 move to the next record.  F3 and F4 allow the user to move to the prior and next field in the current record respectively.  The fifth function key allows the user to change the data in the current field.  When the program is exited or the user moves to a different record the
user will be prompted to verify if the changes to that record are to be saved.  The next two function keys allow the user to change the record links.  It cannot be stressed enough that this should not be done except in the most needful of situations.  Function key 8 will delete the current record.  If this selection is made the user will be prompted as to whether this is really desired.  Any input but 'Y' will be assumed as a no answer.  The last function key, F9 will exit the program.

     5.3  DUMPDF
          This program will sequentially dump the contents of a data file.  Each line displays one field.  Each field is also described by its record, format, and field number. 
No processing of data is performed.  Any compressed or numeric data remains so.

     5.4  DUMPIX
          This utility does a sequential dump of an index.  The number of files that an index refers to is listed.  It will be displayed as "Index is a member of NN datasets".  NN is the number of constituent files.  Each line displays the key, names the file that the key points to, and the record link.

     5.5  MKDF
          This program builds a data file that a DATAMAN process can utilize.  It's usage is:
               mkdf data_file initialization_file.i

          The ".i" extension is required on the initialization file.  mkdf asks the user how many record formats will be defined for that file, then for each format asks the number of fields, and the length of each field.  It then builds the data file based on the information in the initialization file.  All data in the initialization file is separated into fields by colons (":").  The first field of each line is the record format number.  This is a number that ranges from '1' to the highest defined for that file.  The maximum record format number is '63'.  Every record MUST be terminated with a new line.  There can not be a new line character within the body of a record.  If a data field is to be empty when built, the field in the initialization file may be of zero length.  If there is any data in the initialization field, the field must be filled, or padded, to the full length.  Any fields that are not yet built at the time the new line character is encountered will be blank filled.
